# NestJS 연결 계약 — 제안 규격

**사용자의 실제 NestJS 저장소는 이번 작업에 제공되지 않았습니다. 아래는 앱 구현이 기대하는 규격이며 기존 서버와 연결 완료했다는 뜻이 아닙니다.** 경로와 DTO가 다르면 `src/api/repository.ts`, 로그인 화면, 응답 검증을 맞추세요.

## 요청·응답

| 메서드/경로                         | 인증       | 요청                                                                       | 응답                                                                                                  |
| ----------------------------------- | ---------- | -------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| GET `/clinic-categories`            | 불필요     | 없음                                                                       | `[{ id: 82, name: "통증 치료", description: "허리·목·어깨" }]`                                        |
| GET `/appointments/available-slots` | 불필요     | query `clinicCategoryId=82&date=2026-09-19`                                | `[{ appointmentAt: "2026-09-19T10:00:00+09:00", isAvailable: true }]`                                 |
| POST `/auth/login`                  | 불필요     | `{ "email": "...", "password": "..." }`                                    | `{ "accessToken": "..." }`                                                                            |
| POST `/appointments`                | Bearer JWT | `{ "clinicCategoryId": 82, "appointmentAt": "2026-09-19T10:00:00+09:00" }` | `{ "id": 123, "clinicCategoryId": 82, "appointmentAt": "2026-09-19T01:00:00Z", "status": "PENDING" }` |

배열은 현재 래퍼 없는 형식입니다. `description`은 null이 아닌 문자열입니다. ID는 진료 과목에서는 양의 정수, 예약에서는 숫자 또는 문자열입니다. 성공 예약 상태는 `PENDING / CONFIRMED / REJECTED / CANCELLED`를 인식합니다.

앱의 시간 표시와 날짜 경계는 `Asia/Seoul` 기준입니다. PostgreSQL에는 `timestamptz` 등으로 실제 시점을 저장하고 서버에서 한국 운영 시간과 비교하세요. 시간대 없는 문자열은 보내지 않습니다.

## 서버에서 보장할 사항

- `userId`는 요청 본문이 아니라 JWT 검증 결과에서 가져옵니다.
- 생성 상태는 서버가 `PENDING`으로 결정합니다. 사용자에게 ADMIN 역할이나 확정 상태를 입력받지 않습니다.
- DTO/ValidationPipe로 타입, 양수 ID, ISO 날짜를 검증하고 실제 운영일·휴진·예약기간을 서버에서 재검증합니다. 프론트 제한은 보안 장치가 아닙니다.
- 조회 당시 가능했던 시간이 신청 순간에는 마감될 수 있습니다. 신청 시 DB 트랜잭션/정원 규칙으로 다시 확인하고 충돌 시 `409`를 반환합니다.
- `Idempotency-Key` 헤더는 동일 입력 재시도 시 유지됩니다. 사용자+키를 유일하게 저장하고 요청 본문 해시를 비교하여 같은 요청에는 같은 결과를 반환하세요. 키가 같고 입력이 다르면 거절합니다. 헤더만 받는 것으로 중복 방지가 완성되지 않습니다.
- 네트워크 타임아웃 뒤 서버에서는 이미 저장됐을 수 있으므로 앱에서 POST를 자동 재시도하지 않습니다. 수동 재시도는 같은 키를 사용합니다. 앱을 종료하면 키는 사라지므로 예약 이력 조회 및 서버 중복 정책도 필요합니다.
- 401은 재로그인 안내, 409는 시간 재선택, 기타 오류는 일반 실패 안내로 처리합니다. 서버 내부 예외/SQL은 반환하지 않습니다.

## 개발 주소

실물 휴대폰의 `localhost`는 개발 PC가 아닙니다. 같은 Wi-Fi의 PC IP(예: `http://192.168.0.10:3000`)를 설정하고 NestJS는 외부 기기에서 접근 가능한 주소에 listen해야 합니다. Android 에뮬레이터는 `10.0.2.2`, iOS 시뮬레이터는 보통 `localhost`로 개발 PC에 접근합니다.

웹 미리보기에는 CORS가 적용됩니다. NestJS에서 정확한 개발 origin(보통 `http://localhost:8081`)을 허용하고 `Content-Type`, `Authorization`, `Idempotency-Key` 헤더를 허용하세요. 운영에서는 HTTPS를 사용하세요. 네이티브 개발 빌드에서 HTTP가 차단되는 경우 서버 HTTPS 또는 플랫폼 개발 설정이 필요합니다.

## 인증 범위

현재는 access token만 지원하며 만료 시 로그인으로 복귀합니다. 회원가입, refresh token/rotation, 서버 로그아웃·폐기, 내 예약 목록 API는 미구현입니다. SecureStore 저장이 토큰의 유효성 검증을 대신하지는 않습니다. 마이페이지의 저장 상태 표시도 서버 인증 성공을 보장하는 표시는 아닙니다.

API 모드 검증은 실제 병원 서버가 아닌 Playwright의 HTTP 응답 대역으로 합니다. 실서버 연동 검증은 서버 구현 후 별도로 진행해야 합니다.
